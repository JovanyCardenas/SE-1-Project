# Spartan Academic Planner (SAP) — Technical Specification & Roadmap

## 1. Project Overview & Vision

The **Spartan Academic Planner** is a student-focused academic planning and productivity platform designed to turn course information into an actionable semester plan.

The core idea is to reduce repetitive manual work. A student should be able to join a course, upload or use an existing syllabus, and automatically receive the shared assignments, exams, quizzes, deadlines, and course events that apply to everyone in that exact class. Students can then add their own private assignments, reminders, study sessions, and other personal events without changing the shared course data.

The planner will focus on:

- Automatically parsing course syllabi into assignments, exams, quizzes, deadlines, grading information, and course events.
- Reusing shared course data when multiple students are enrolled in the same exact class.
- Clearly distinguishing shared course items from student-created personal items.
- Allowing students to manually create assignments and events linked to a course.
- Supporting calendar importing and **two-way calendar synchronization**, including Google Calendar.
- Helping students understand upcoming workload and plan study time.
- Supporting communication between students enrolled in the same course while respecting user privacy settings.
- Providing a foundation for future grade projections, workload estimation, customizable dashboards, and additional academic planning tools.

## 2. Core Product Principles

### Shared Once, Personalized Per Student

A course should not need to be recreated or re-parsed separately for every student.

If multiple users are enrolled in the same exact course offering, they should share:

- Course information
- The course syllabus
- Syllabus parsing results
- Syllabus-generated assignments
- Syllabus-generated exams and quizzes
- Syllabus-generated course events
- Shared grading categories and course-level deadlines

Each student should still have their own private layer containing:

- Manually added assignments
- Personal reminders
- Study sessions
- Personal events
- Personal completion status
- Personal notes
- Personal estimated effort
- Personal grade/score information
- Calendar synchronization preferences

This separation allows shared academic information to be reused without exposing private student data.

### Source Transparency

Every assignment or event should indicate where it came from.

Example source types:

- `SYLLABUS` — automatically extracted from the shared syllabus
- `CALENDAR_SYNC` — imported from a linked external calendar
- `MANUAL` — created directly by the student
- `SYSTEM` — generated by the planner from another supported feature

Students should be able to quickly tell the difference between official/shared course information and something that only exists in their personal planner.

## 4. Core Data Model

### A. Course

A `Course` represents one exact course offering that can be shared by multiple users.

Required course fields:

- `class_name` — full class name, such as `Software Engineering I`
- `short_name` — short course code/name, such as `CMPE 131`
- `course_section` — section identifier, such as `04`
- `semester` — such as `Fall`, `Spring`, or `Summer`
- `year` — such as `2026`
- `syllabus_file` — syllabus associated with this exact offering

Recommended supporting fields:

- `instructor`
- `institution`
- `syllabus_hash`
- `created_at`
- `updated_at`

A course should be reusable by many students through `CourseEnrollment`.

### B. Identifying the Same Exact Course

The system should avoid creating duplicate course records when students are taking the same exact class.

A course match should primarily consider:

```text
short_name
+ course_section
+ semester
+ year
+ institution
```

The syllabus file/hash can be used as an additional verification signal.

If the identifying information matches but a newly uploaded syllabus is materially different, the system should require verification rather than silently overwriting the existing shared course.

### C. Course Enrollment

`CourseEnrollment` links a student to a shared `Course`.

Example fields:

- `user`
- `course`
- `joined_at`
- `status`
- `display_to_classmates`

This relationship allows many students to use the same shared syllabus and course-generated assignments while maintaining separate personal planner data.

## 5. Shared Course Items vs. Personal Student Items

### Shared Course Assignment

A `CourseAssignment` represents an assignment, exam, quiz, project milestone, or other deliverable that applies to the course as a whole.

Example fields:

- `course`
- `title`
- `description`
- `item_type`
- `due_at`
- `points_possible`
- `grading_category`
- `source`
- `source_reference`
- `parser_confidence`
- `is_verified`

Shared items normally come from the syllabus parser and are visible to every student enrolled in the course.

### Student Assignment State

Personal information should not be stored directly on the shared assignment.

A separate `StudentAssignment` record should connect the user to a shared `CourseAssignment`.

Example fields:

- `user`
- `course_assignment`
- `completed`
- `score_earned`
- `estimated_hours`
- `personal_notes`
- `personal_due_override`
- `hidden`
- `created_at`
- `updated_at`

This allows two students to share the same course assignment while having different completion states, grades, notes, and planning estimates.

### Manual Student Assignment

Students must also be able to create assignments that were not found in the syllabus.

A manual assignment:

- Belongs to one student.
- May optionally be linked to a course.
- Is private by default.
- Uses `source = MANUAL`.
- Does not become a shared course assignment automatically.
- Should be visually marked as student-created.

If a manual item appears useful as a correction to the shared course, a future workflow may allow a student to suggest it for shared-course review without automatically exposing the student's private record.

### Planner Events

Students can create personal events such as:

- Study sessions
- Office hours reminders
- Group meetings
- Advising appointments
- Personal deadlines
- Work or life events that affect study planning

Events may optionally link to a course but remain private unless explicitly shared.

## 6. Syllabus Parser & Automatic Item Creation

### A. Upload and Reuse Flow

1. A student searches for or creates a course.
2. The system checks whether the exact course offering already exists.
3. If the course already exists with a verified syllabus, the student can join the existing course instead of uploading and parsing the syllabus again.
4. If no verified syllabus exists, an authorized student can upload the syllabus.
5. The syllabus is parsed once for the shared course.
6. Parsed results go through a verification/review stage.
7. Approved items become shared `CourseAssignment` or course event records.
8. Every enrolled student receives the shared course items in their planner.

### B. Parser Targets

The syllabus parser should attempt to extract:

- Assignment names
- Homework
- Projects and milestones
- Quizzes
- Exams and midterms
- Final exam information
- Due dates
- Due times when available
- Recurring class-related events
- Important course dates
- Grading categories
- Grade weights
- Points possible when available

### C. Verification

Parser output should not immediately become trusted course data when confidence is low.

The parser should support:

- Confidence indicators
- Preview before publishing
- Editing incorrect titles or dates
- Removing false detections
- Adding missing syllabus items
- Marking records as verified

Once approved, the shared records should be reused for students who later join the same exact course.

## 7. Calendar Importing and Two-Way Synchronization

Calendar support should go beyond a one-time `.ics` export.

The planner should support linked external calendars, with **Google Calendar as the primary planned integration**.

### A. Calendar Connection

A student should be able to:

1. Connect their Google account.
2. Choose an existing Google Calendar or create/select a dedicated Spartan Academic Planner calendar.
3. Choose which calendar(s) are linked to SAP.
4. Enable or disable synchronization for each linked calendar.

### B. Google Calendar -> Spartan Academic Planner

When an event is created, edited, or deleted in a linked Google Calendar, the corresponding event should be created, updated, or removed from the student's planner when synchronization runs.

Imported records should:

- Use `source = CALENDAR_SYNC`.
- Store the external Google Calendar event ID.
- Store the linked external calendar ID.
- Be associated only with the authenticated student's account unless the user explicitly converts/shares it.
- Avoid duplicate imports.

### C. Spartan Academic Planner -> Google Calendar

When a synchronized event or assignment is created or changed in SAP, the corresponding Google Calendar event should also be created or updated.

Examples:

- A student creates a manual study session in SAP -> it appears on the selected Google Calendar.
- SAP adds a syllabus-generated assignment to the student's synced calendar -> the external calendar receives the deadline.
- A student changes a synchronized event time in SAP -> Google Calendar receives the update.

### D. Sync Mapping

A `CalendarSyncRecord` should maintain the relationship between internal and external records.

Example fields:

- `user`
- `calendar_connection`
- `external_calendar_id`
- `external_event_id`
- `content_type`
- `object_id`
- `last_internal_modified_at`
- `last_external_modified_at`
- `last_synced_at`
- `sync_status`

This prevents duplicate events and allows updates to flow in both directions.

### E. Conflict Handling

If the same event changes in SAP and Google Calendar before synchronization, the system should detect the conflict instead of silently losing data.

An initial strategy may use:

- Latest modification timestamp
- A visible conflict warning
- A user choice between the SAP version and Google Calendar version for ambiguous conflicts

### F. Additional Calendar Support

The architecture should allow future integrations such as:

- Apple Calendar
- Outlook / Microsoft 365
- Standard iCalendar feeds

Standard `.ics` export/subscription may still be supported for calendars that do not have a full two-way integration.

## 8. Student Discovery, Privacy, and Messaging

Students enrolled in the same course should be able to discover and communicate with classmates.

### A. Classmate Directory

A course page may include a classmate list showing students who are enrolled in that same `Course`.

For a normal/public account, classmates may see allowed profile information such as:

- Display name
- Profile photo/avatar
- Major or other optional profile information
- A button to start a conversation

### B. Private Account Mode

Students must be able to set their account to **private**.

When private mode is enabled:

- Other classmates should not see the student's identifying profile information in the normal classmate directory.
- Other students cannot initiate direct communication with that private user.
- The private user can still browse the course and use all personal academic features.
- The private user may initiate communication with another student.

### C. Privacy Reveal After Student-Initiated Contact

If a private user chooses to contact another student first:

1. A conversation is created.
2. The private user becomes identifiable to the recipient within that conversation.
3. The recipient can reply and continue communicating.
4. The private user's identity does not automatically become public to the rest of the course.

This creates a relationship-scoped privacy exception rather than disabling privacy globally.

### D. Messaging Safety and Controls

Students should be able to:

- Block another user.
- Leave or archive a conversation.
- Report inappropriate messages.
- Disable future contact where applicable.

Private academic information such as grades, personal assignments, notes, calendar events, and synced external events must never be exposed through the classmate system.

## 9. Smart Workload & Academic Planning

The planner should combine shared course deadlines with the student's private schedule.

Potential planning features include:

- Weekly assignment count
- Estimated study hours
- Upcoming deadline timeline
- Workload indicators
- "Crunch week" warnings
- Personal study-block scheduling
- Completion tracking
- Grade projection / hypothetical grade scenarios

Example workload calculation:

```text
Weekly Estimated Workload =
sum(student estimated hours for assignments due during that week)
```

The system should treat workload estimates as personal data because different students may need different amounts of time for the same assignment.

```text
   ↓

   ↓

   ↓
```

```text

   ↓
Optionally link to course
   ↓
Mark source as MANUAL
   ↓

   ↓
```

```text
   ↓
```

## 13. Security & Data Protection Requirements

- Require authentication for student planner and course features.
- Enforce object-level permissions for all personal planner data.
- Keep shared course data separate from student-specific data.
- Never expose student grades, scores, personal notes, personal events, or linked calendar data to classmates.
- Respect private-profile communication rules on both UI and backend endpoints.
- Protect external calendar OAuth credentials/tokens.
- Use the minimum calendar permissions necessary for the selected sync features.
- Validate and sanitize syllabus uploads.
- Limit accepted syllabus file types and file size.
- Do not automatically trust parser output without a verification path.
- Keep an audit trail for important shared-course changes when practical.

## 14. Testing Priorities

### Course Sharing

- Two students joining the same exact course should reference the same `Course`.
- Shared syllabus assignments should not be duplicated for each user.
- Personal completion status and grades must remain independent.

### Syllabus Parsing

- Correctly identify supported assignment/date formats.
- Preserve uncertain results for verification.
- Prevent duplicate shared assignments when a syllabus is parsed again.

### Personal vs. Shared Data

- Manual assignments must remain visible only to their creator unless intentionally shared.
- Personal notes, scores, and workload estimates must never leak across students.

### Privacy & Messaging

- Private users must not expose identifying information in the normal classmate directory.
- Other users must not be able to initiate messages to a private user.
- A private user who initiates a conversation should become identifiable only within that conversation.

### Calendar Sync

- SAP-created events should be created in the selected Google Calendar.
- Google Calendar-created events should appear in SAP.
- Updates and deletions should synchronize without creating duplicates.
- Sync mappings must remain user-specific.
- Conflicts should not silently overwrite both versions.
